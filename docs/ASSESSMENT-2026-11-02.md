## 二、外部约束核实（决定路线，不只是合规清单）

### 1. 虚拟支付：个人主体已可收款，变现路径成立

- 2026-08-31 起，个人主体 + 工具类目 + 已完成认证备案的小程序可开通虚拟支付，月收款上限 10 万元；
  费率 Android 1%（T+3）、iOS 12%（45–60 天结算）。来源：二手解读（CSDN/百家号），**待微信官方文档复核**。
- 对项目的影响：现有 `cloudfunctions/{createVirtualOrder,virtualPayNotify,getEntitlement}` 的单份报告付费模式
  在规则上是可行的；iOS 端 12% 费率意味着 990 分（9.9 元）到手约 8.7 元。
- 待确认：`paySig` 的签名 uri、`XPAY_*` 环境变量需与当期官方文档逐项对齐（README 已列为上线前必核）。

### 2. AI 备案：调用已备案模型只需「登记」，不是「备案」

- 官方口径（网信办 2026-09 公告）：通过 API 直接调用已备案模型能力的应用，由**地方网信办开展登记**；
  截至 2026-08-31，累计 1112 款完成备案、731 款完成登记。来源：`cac.gov.cn` 官方公告，可信度高。
- 登记材料：登记表 + 模型服务协议；审查重点是「调用模型是否已备案、协议是否合法、自身有无内容审核能力」。
  来源：腾讯云开发者社区解读，**中等可信，需以属地网信办要求为准**。
- **对总纲的修正**：`AIGC 备案` 与 `登记` 是两件事。项目若只调用通义/豆包/文心等已备案模型做「解释」，
  走登记即可，不必等「备案」。这解除了 AI 解释层的一部分阻塞，但**内容审核能力（关键词 + 人工兜底）必须先具备**。

### 3. 内容审核：这是产品第一约束，不是事后包装

- 微信明确将「算命、看相、占卜」及「借服务名义采集生辰八字」列为违规，并禁止「杜撰受益案例兜售风水咨询」。
  来源：微信官方公告（2024-08，仍在执行）+ 开发者社区。
- 项目当前用「传统人居环境与方位信息的记录工具」「先人纪念地环境建档」表述，是正确规避。
- **风险点仍在择日模块**：一旦 UI 出现「吉日/凶日/必发/化解」，即落入违规描述。
  现有措辞（「传统规则条件下的筛选结果」）方向对，但需逐页扫描，尤其是报告页与分享图。

### 4. 星历许可：Swiss Ephemeris 只能做开发期基准

- 双许可：AGPL（传染整项目）或商业 Professional License。来源：官方 LICENSE + 多篇技术文，可信度高。
- 项目定位「仅开发期校验基准」是正确的；**但不得把 `se1` 星历文件打进产物**，也不得让 `pyswisseph` 进入运行时依赖。
  现有 `tests/fixtures/swisseph-solar-2026.json` 固定校验数据，是安全做法。

### 5. 地图：走天地图官方 API，个人可申请 Key

- 天地图是国家地理信息公共服务平台，提供矢量/影像/地形晕渲底图，页面公示测绘资质编号。
  来源：`lbs.tianditu.gov.cn` 官方站点，可信度高。
- 个人开发者用官方底图 + 官方 API 属合规路径；**自建底图、无人机航拍、点云建模**才涉及测绘资质与空域问题。
- 对 GIS 模块的影响：底图选型不必纠结，直接用天地图；真正的工作量在 DEM 处理与指标计算。

### 6. VSOP87 精度：0.001° 目标偏乐观

- VSOP87 全量理论对行星黄经精度约 1″（≈0.0003°）；截断到 L0 前数十项后，典型误差 0.01°–0.1°。
  来源：NASA 日食预测页（VSOP87 用于日月食计算）+ 技术综述，可信度中高。
- **对总纲的修正**：天星七政若目标 0.001°，需保留大量级数项并加摄动修正，工作量远超「补几项截断」。
  建议把目标改为**分层公布误差界**：太阳/月亮 ≤0.02°（择日够用），五星 ≤0.1° 并标 `PARTIAL`，
  四余维持不可用。这比许诺 0.001° 再达不到更符合「不伪造」原则。

## 三、开发路线修正建议

总纲的顺序是 `#24 → #23 → 阳宅 → 阴宅 → GIS → 3D → AI → 打包`。整体方向对，但有三处需要调整。

### 调整一：#24 必须先「闭合」，不是「开工」

数据层已就绪，但三个缺口让它还不能算完成：

1. **桌面 IPC 未接**：`desktop/src/` 里没有任何一处调用 `loadArchives/saveArchives/exportArchives`。
2. **结果快照未存**：`Archive` 只存输入，`attributeDiff()` 需要 `EvaluationSnapshot`（inputHash + rulePackVersion + verdict + 排除天数），
   但没有任何地方把评估结果写进档案。**没有快照，diff 归因永远跑不起来。**
3. **迁移失败项无 UI**：`migrationFailures` 已在 store 里，但没有页面展示。

这三件是同一个闭环，建议一次做完，约 1–2 天。

### 调整二：#23 不是「搬文件」，是「先统一多派输出 schema」

现在 `bazhai.ts` / `xuankong.ts` / `feixing.ts` 各返回自有结构，无法并列展示，也无法套用择日已有的
`SchoolResult`（`school/status/tendency/scoreDelta/subRules/conflictFlags/needsHumanReview`）。

**正确顺序**：先定义 `PaipanSchoolResult`（可复用 `SchoolResult` 形状）→ 三个引擎各出一个 adapter →
再谈目录迁移。否则搬完文件仍然是三套形状，等于没搬。

### 调整三：GIS/3D 应该「极简做」，而不是排在第 5/6 位大投入

理由不是工期，是**认识论**：形峦判断本质是经验断言（「明堂开阔为吉」「水口关锁为吉」），
用算法算「开阔度」「关锁度」再输出吉凶，正是项目最反对的「把断言包装成客观指标」。

建议明确划线：

- GIS **只做三个客观指标**：坡度、坡向、日照时长（公开 DEM + 天地图底图），输出为「地形事实」，不带吉凶。
- 3D **只做两件事**：建筑体量与视线遮挡、户型体量与门窗位置。不做「明堂评分」「案山评分」。
- 来龙走向、过峡位置、水口吉凶**一律标「需实地勘测」**，不给算法结论。

这样 GIS/3D 从「大模块」降为「两个小工具」，反而更容易做成且不损害可信度。

## 四、优化建议

### 架构层

1. **`core/engines/` 命名混乱**：里面同时有排盘（bazhai/xuankong/feixing/xianming）、择日编排（zeri.ts）、
   报告（report.ts）。建议拆为 `core/paipan/`（排盘三派）、`core/app/`（编排）、`core/zeri/`（择日），
   让「一个目录一个职责」成立。
2. **阳宅/阴宅复用择日的分层纪律**：`SchoolResult` + `conflictFlags` + `needsHumanReview` 这套形状是资产，
   不要为阳宅另造一套「吉凶评分」。
3. **档案与评估解耦但要对得上**：`Archive` 存输入与 `inputHash`，另存一份 `lastEvaluation`
   （`EvaluationSnapshot` + 生成时间 + 规则包版本），diff 才有对比基准。

### 工程层

4. **桌面端是主攻方向，但功能只有择日**：`App.vue` 三栏工作台只接了 `buildZeRi`。阳宅/阴宅排盘在小程序里有、
   桌面端没有，等于两条产品线功能不对等。建议明确「桌面 = 专业工作台（择日 + 排盘 + 档案）」，
   「小程序 = 现场采集 + 轻查看」，避免两边都做一半。
5. **报告页 1742 行需要拆**：按「结论 / 大煞分区 / 五派并列 / 口径与出处 / 免责」拆成子组件，
   否则每次改文案都要动一个大文件，且难以做快照测试。
6. **补多派冲突测试**：现有 `tests/schools.test.ts` 覆盖规则包，但缺「同一日课两派相反」的端到端用例。
   择日已有 `conflict_flag`，排盘还没有。

### 产品层

7. **差异化要「看得见」**：竞品（通胜万年历、全能黄历通）都是黑盒黄历 + 吉凶断言。
   你的优势是「出处 + 冲突 + 数据缺口」，但如果报告里这些藏在折叠区，用户感知不到。
   建议在结论卡片上直接给三个徽标：`出处 n 条` / `分歧 n 处` / `缺口 n 项`，点开才是详情。
8. **付费点建议调整**：单份报告 990 分在 iOS 12% 费率下利润薄。建议
   「档案与导出免费、报告解锁付费、批量择日（多月/多年）作为高阶付费」，用档案沉淀换复购。
9. **文案红线自查清单**：择日页禁止「吉日/凶日/宜忌/化解/转运/必发」；统一为「传统规则筛选」「排除项」「提示项」。
   分享图尤其危险，容易被截图传播后被判违规。

### 数据层

10. **规则考证是真正的瓶颈，不是代码**：`verification_status` 全为 `unverified` 是诚实，但产品价值受限。
   建议优先考证**影响排除判定的少数规则**（岁破、月破、三煞占山、四离四绝、冲山冲命），
    而不是平均用力。考证完成一条，报告的可信度就上一个台阶。
11. **古籍原文检索是低成本差异化**：《协纪辨方书》为公版，可做「点规则看出处原文」。
    竞品做不到这一点，而它恰好是「可审计」最直观的体现。

## 六、一句话结论

总纲的分层与纪律是对的，代码在择日这条线上也确实做到了「多派并列、出处可追溯、冲突显式」。
真正需要修正的不是架构，而是**三处判断**：档案库已过半而非未开工、AI 只需登记而非备案、
GIS/3D 应极简而非大投入。把 #24 闭合、把多派 schema 统一、把文案红线守住，
这个系统就能从「一个很讲究的择日工具」变成「一套可审计的环境决策辅助系统」。
