# ADR-0003：规则 DSL 的设计与扩展

- 状态：已采纳
- 日期：2026-11-01
- 决策者：实现者（Agent），待人类复核

## 背景

上游规格给出 `{all/any/not}` + `{fact, op, value}` 的原子节点，算子含 `eq/ne/in/nin/intersects/gte/lte/between/exists/same_group`。
实现时发现两类表达力缺口：

1. **动态比较**：规则需要判断"坐山是否落在三煞方位内"，而三煞方位是运行时计算的列表。
   规格的 `value` 只能是字面量，无法引用另一条路径。
2. **集合计数**：结构检测产生的是列表（如 `zixing_pairs`），规则需要判断"是否存在至少一条"。
   规格无计数算子，只能靠遍历，违反"规则即数据"。

## 决策

在**不破坏原有语法**的前提下扩展三项：

1. `value_from: <path>`：原子节点可用上下文中的另一条路径作为比较值。
   ```yaml
   - fact: facts.taisui.zhi
     op: eq
     value_from: site.shan_jia_zhi
   ```
2. `same_group` 的 `value` 扩展为 `{path: ..., kind: sanhe|sanhui|liuhe|chong|hai|xing|po}`。
3. 新增 `count_gte` / `count_eq`：对列表/字典/字符串取长度比较。

## 理由

- 三者都只是"取值方式的扩展"，不引入新的判定语义，不违反"禁止旁路求值器"。
- 若不扩展，规则库会被迫写死具体山名/干支，导致"一条规则拆成 24 条"，违背"规则即数据"。
- 扩展点全部在 `core-rule/dsl.py` 的 `OPS` 表与 `_eval_atom` 中，可被单一测试覆盖（算子全覆盖测试）。

## 后果

- ✅ 42 条规则即可表达全部公共否决层，且每条都是纯数据。
- ⚠️ `value_from` 增加了路径解析的复杂度；已通过白名单校验（加载期即拒绝越界路径）控制风险。
- ⚠️ 规格文档需同步更新（已在 `docs/DEVELOPMENT.md` 5.2 节补充）。

## 未采纳的备选

| 方案 | 否决理由 |
|---|---|
| 在规则里写 Python 表达式 | 无法静态校验、可执行任意代码、违反"规则即数据" |
| 用 JSONLogic | 引入外部依赖，且其语义与三值逻辑不完全一致 |
| 允许规则内嵌 Jinja 模板 | 同上，且模板可执行逻辑，审计困难 |
